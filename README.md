# WiFi-NetPulse

WiFi-NetPulse measures network download/upload speed, latency, jitter and packet loss, stores measurements, and displays trends with an ML-based speed prediction dashboard.

## Deployment architecture

- **Render** hosts the Flask dashboard/API using Gunicorn.
- **Neon PostgreSQL** stores measurements and alerts.
- **GitHub Actions** runs `collector.py --once` every 15 minutes and writes measurements to Neon.
- The trained model artifacts in `models/` are loaded by the prediction API.

> Important: a collector running on GitHub Actions measures the GitHub runner's network connection, not your hostel/home Wi-Fi. To monitor your own Wi-Fi, run the collector on a device connected to that network and send its measurements to the hosted database/API. Cloud collection is useful for monitoring the cloud runner's connectivity and demonstrating the deployment architecture, but it is not a substitute for a local network agent.

## Run locally (SQLite)

Python 3.11 is recommended. The scikit-learn version is pinned to match the included model artifacts.

```bash
python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
python database.py
python app.py
```

Open `http://127.0.0.1:5000`. In another terminal, activate the same environment and run:

```bash
python collector.py --once
# Or run continuously every 15 minutes:
python collector.py --interval 15
```

When `DATABASE_URL` is not set, the application uses the local `wifi_monitor.db` SQLite file. When `DATABASE_URL` is set, it uses PostgreSQL through SQLAlchemy and psycopg.

## Deploy to Neon + Render + GitHub Actions

### 1. Create the Neon database

1. Create a Neon project and database.
2. Copy its PostgreSQL connection string (prefer the pooled connection string for a serverless web app if Neon offers one).
3. Keep the connection string private. Do not commit it, paste it into source code, or share it in chat.
4. Ensure the connection string includes SSL (`sslmode=require`). The application also enforces SSL for Neon hosts.

### Optional: preserve existing local SQLite history

If you have an existing `wifi_monitor.db` that you want to keep, first create an empty Neon database, then run this from your project folder in PowerShell:

```powershell
$env:DATABASE_URL = "YOUR_NEON_CONNECTION_STRING"
python migrate_sqlite_to_postgres.py .\wifi_monitor.db
Remove-Item Env:DATABASE_URL
```

Do not paste the real connection string into source code or commit it. The migration script refuses to copy into destination tables that already contain rows, to reduce the risk of duplicates. If you do not have an existing SQLite database or do not need its history, skip this optional step.

### 2. Deploy the web app to Render

1. Push this repository to GitHub.
2. In Render, choose **New → Blueprint** and select this repository; Render will read `render.yaml`.
3. When prompted, add `DATABASE_URL` using the Neon connection string. `ADMIN_API_KEY` is generated by the Blueprint; keep it private.
4. Deploy and wait for the build to finish.
5. Open `https://YOUR-SERVICE.onrender.com/api/status`. A successful response has `status: "ok"`.
6. Open the service root URL to view the dashboard.

The Render free web service may sleep after inactivity and can take time to wake. Confirm current Render plan limits before relying on continuous availability.

### 3. Configure the scheduled collector

1. In GitHub, open **Settings → Secrets and variables → Actions**.
2. Create a repository secret named `DATABASE_URL` and paste the same Neon connection string.
3. Open **Actions**, enable workflows if prompted, then run **WiFi-NetPulse scheduled collection** manually once using **Run workflow**.
4. Check the workflow run logs. A successful run should initialize the schema and finish a collection cycle.
5. Scheduled runs are configured every 15 minutes. GitHub may delay scheduled workflows; they are not guaranteed to start at the exact minute.

GitHub Actions collection measures the GitHub-hosted runner's network. It does not measure the Wi-Fi network of your laptop/hostel. For personal Wi-Fi monitoring, run a local agent on the target network and securely send its measurements to the hosted database.

## Security and operations

- `DATABASE_URL` and `ADMIN_API_KEY` belong in provider secrets/environment variables, never in Git.
- `/api/collect` and `/api/ml/train` require the `X-Admin-Key` header matching `ADMIN_API_KEY`; they are disabled if no key is configured.
- The dashboard and API are served from the same origin. CORS is not opened to arbitrary websites.
- Render's local filesystem is ephemeral. The checked-in model files are available after deploy, but model files retrained at runtime may be lost after a restart/redeploy. Retrain locally, verify the artifacts, and commit updated model files, or configure durable object storage before enabling persistent online retraining.
- `wifi_monitor.db` is for local development only. Production data belongs in Neon PostgreSQL.
- Database timestamps are stored in UTC. Daily summaries, hourly buckets, and ML time features use `APP_TIMEZONE` (default: `Asia/Kolkata`).

## API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/status` | Service health |
| GET | `/api/latest` | Latest measurement |
| GET | `/api/history?hours=24` | Measurement history |
| GET | `/api/hourly?days=7` | Hourly aggregates |
| GET | `/api/summary` | Today's summary (UTC) |
| GET | `/api/alerts?limit=10` | Recent alerts |
| GET | `/api/stats/peak-hours` | Average speed by hour |
| GET | `/api/ml/predict?hours=6` | ML predictions |
| GET | `/api/ml/best-hours` | Best predicted usage hours |
| GET | `/api/ml/info` | Model metadata |
| POST | `/api/collect` | Manual collection (admin key required) |
| POST | `/api/ml/train` | Model training (admin key required) |
